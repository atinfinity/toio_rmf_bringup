# 章2: RMFの全体像を掴む

← [前章: Open-RMFとは](01_overview.md) | [目次](README.md) | 次章: [1台を動かす →](03_go_to_place.md)

## 狙い

- Open-RMFの環境が**3つの層**でできていることを、実際のノード一覧から掴む
- 「タスクを投げてからキューブが動くまで」に、どのノードが何を担当するかの
  地図を頭に描く。この地図が以降すべての章の土台になる。

## 三層モデル

toioフリートの環境は、役割の違う3層が重なってできている。上ほど「何をするか」、
下ほど「どう動かすか」を担当する。

```
┌─────────────────────────────────────────────┐
│ ① RMFコア     … 仕事を配る・交通を捌く         │  「誰が・いつ・どこへ」
│   rmf_task_dispatcher / rmf_traffic_schedule  │
│   rmf_traffic_blockade / building_map_server  │
├─────────────────────────────────────────────┤
│ ② フリートアダプタ … RMFとロボットの通訳       │  「このロボットで実現する」
│   toio_fleet_adapter (EasyFullControl)        │
├─────────────────────────────────────────────┤
│ ③ ロボット層  … 実際に走らせる                 │  「どう走るか」
│   Nav2 /toio1・/toio2  +  Gazebo(または実機)  │
└─────────────────────────────────────────────┘
```

- **① RMFコア**は、ロボットの機種を知らない。「patrol_Aへ行け」「この時刻に
  このレーンを予約する」といった**抽象的な指示**だけを扱う。
- **③ ロボット層**は、RMFを知らない。`NavigateToPose` アクションで
  「この座標へ行け」と言われたら走る、ただのNav2ロボット。
- **② フリートアダプタ**が両者の通訳。RMFの抽象タスクを受け、Nav2の
  `NavigateToPose` に翻訳し、逆にロボットの位置・バッテリをRMFへ報告する。
  toioでは `toio_fleet_adapter`(RMFの **EasyFullControl** API 実装)がこれ。

この分業のおかげで、**RMFコアの上で学ぶこと(入札・調停・充電)は、下の
ロボットがシミュレーションでも実機でも同じ**になる。章11で実機に移っても、
差し替わるのは③だけ。

## 動かす・観察する

端末Aで環境を起動したまま([章0](00_setup.md)の端末A)、端末Bで中を覗く。

### 1. ノードを層ごとに見分ける

```bash
ros2 node list
```

出てくるノードを上の3層に振り分けてみる:

| 層 | 主なノード |
|---|---|
| ① RMFコア | `rmf_task_dispatcher`、`rmf_traffic_schedule_primary`、`rmf_traffic_blockade`、`building_map_server`、可視化ノード群 |
| ② アダプタ | `toio_fleet_adapter`(フリート名 `toio`) |
| ③ ロボット | `/toio1/*`、`/toio2/*`(Nav2のcontroller / planner / bt_navigator など、名前空間付きで各1式) |

名前空間 `/toio1` `/toio2` が付いているものが**ロボット1台ぶんのNav2**。
2台なので2セットある。名前空間の無いRMF・アダプタ系は**フリート全体で1つ**。

### 2. タスクの入口を見る

RMFコアへの入口はトピック。タスクCLIはここに投げている:

```bash
ros2 topic list | grep -E 'task|dispenser|ingestor'
```

`/task_api_requests` などが見える。[章3](03_go_to_place.md)以降で投げる
`dispatch_*` コマンドは、最終的にここへ届く。

### 3. フリートの自己申告を聞く

アダプタが定期的に流している**フリートの状態**を覗く:

```bash
ros2 topic echo /fleet_states --once
```

フリート名 `toio`、ロボット `toio1` / `toio2`、それぞれの現在位置とバッテリ
残量が入っている。**これがRMFコアから見た「ロボットの姿」**。RMFコアは
キューブそのものではなく、この報告を通してロボットを認識している。

## 理解する

- ③のロボット層は、実は**このパッケージ独自ではない普通のNav2**。RMFは
  `NavigateToPose` アクションを名前空間付きで叩いているだけ。だから
  「Nav2が単体で動く」ことは前提で、RMFはその上に**協調の頭脳**を乗せている。
- ①と②の境界が、このチュートリアルの主戦場。**入札(章5)・交通調停(章6)・
  充電計画(章7)は①で決まり、②がそれをロボットの言葉に翻訳する**。
- 位置とバッテリの報告経路は覚えておくと章11で効く。**走行指令は②→③
  (`NavigateToPose`)へ下るが、位置・バッテリは③→②へ別経路で上がる**。
  シミュレーションではTF(`map`→ベースフレーム)から、実機では
  `toio_ros2` の専用トピックから受け取る(→[章11](11_real_robot.md))。

より詳しい構成図(どのノードがlaunchされるか)は
[README のパッケージ構成図](../../README.md)にある。

## 確認課題

1. `ros2 node info /toio1/bt_navigator` などで、Nav2側が
   `navigate_to_pose` アクションサーバを提供していることを確認する。
   これがフリートアダプタの「委譲先」。
2. `/fleet_states` をechoしたまま、[章0](00_setup.md)のpatrolをもう一度
   投げてみる。ロボットの `mode` や位置がタスク中にどう変わるか眺める
   (詳しい読み方は次章)。

三層の地図が描けたら、いよいよ一番下の「1台を1回動かす」から積み上げる。
