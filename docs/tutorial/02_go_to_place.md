# 章2: 1台を動かす(go_to_place)

← [前章: RMFの全体像](01_architecture.md) | [目次](README.md) | 次章: [巡回と帰還 →](03_patrol.md)

## 狙い

- RMFで一番単純なタスク **go_to_place**(指定地点へ1回だけ移動)を投げる
- 「タスクを投げてから、フリートアダプタがNav2に走行を委譲するまで」の
  一連の流れを、実際にログとアクションで追う
- **特定の1台**を指名して動かす方法を知る(入札を経ない直接割当)

前章の三層モデルを、1本の最小タスクで縦に貫く章。

## 動かす

端末Aは起動したまま。端末Bから、目的地を1つ指定して移動させる:

```bash
ros2 run rmf_demos_tasks dispatch_go_to_place -p patrol_B --use_sim_time
```

`-p patrol_B` が目的地(navグラフの頂点名)。どちらか空いている1台が
`patrol_B` へ向かい、着いたら**そこで停止する**(patrolと違い巡回も帰還も
しない)。

### 特定の1台を指名する

入札(次章以降)を経ず、名指しで動かすこともできる:

```bash
ros2 run rmf_demos_tasks dispatch_go_to_place -p patrol_B -F toio -R toio1 --use_sim_time
```

- `-F toio` … フリート名(このパッケージでは常に `toio`)
- `-R toio1` … ロボット名。`-F` と併用したときだけ有効で、**入札を経ず
  そのロボットへ直接割り当てる**(RMF内部では `robot_task_request`)

`-F` を付けず `-R` だけ、あるいは両方無しなら、フリート内で**入札**して
勝った方が動く(→[章4](04_bidding.md))。

## 観察する

### 1. タスクの一生をログで追う

端末Aの `rmf_task_dispatcher` と `toio_fleet_adapter` のログに、投入から完了
までが流れる。おおまかに次の順で読める:

1. ディスパッチャがタスク要求を受ける
2. フリートへ **BidNotice**(入札依頼)が飛ぶ
3. アダプタが **BidResponse**(到達時刻とバッテリ消費の見積)を返す
4. ディスパッチャが**落札通知**(`task_id` を割当)
5. アダプタがNav2へ `NavigateToPose` を発行 → キューブが動く
6. 到達後、`TaskState` が `completed` になる

`-R` で直接指名した場合は 2〜4 の入札が省かれ、いきなりそのロボットに割り
当たる。ここが「入札あり / なし」の見分けどころ。

### 2. 委譲先のアクションを覗く

フリートアダプタが実際に叩いているNav2のアクションを、別端末で監視してみる:

```bash
ros2 topic echo /toio1/navigate_to_pose/_action/status
```

タスクを投げた瞬間、指名した(または落札した)ロボットのこのトピックに
ゴールが現れ、`STATUS_EXECUTING`(=4)になる。**RMFの抽象タスクが、
ここでNav2の具体的な座標移動に翻訳されている**瞬間が見える。

### 3. 位置がどこから来ているか確かめる

RMFはキューブの位置をTFから受け取っている(シミュレーション時)。走行中に:

```bash
ros2 run tf2_ros tf2_echo map toio1/base_link
```

`map` からの座標が刻々と更新される。この値が `/fleet_states`([章1](01_architecture.md))
のロボット位置と一致しているはず。**「走行指令は下りるが、位置は別経路で
上がる」**という前章の話が、ここで具体的に確認できる。

## 理解する

- **go_to_placeは「移動」だけのタスク**。RMFのタスクは「移動」「荷役」
  「充電」などの**フェーズの列**でできていて、go_to_placeはその最小構成
  (移動フェーズ1つ)。patrol(章3)やdelivery(章7)は、このフェーズを
  組み合わせたもの、と捉えると見通しが良い。
- **走行はNav2に丸投げ**。RMF/アダプタは「どの頂点へ」までを決め、頂点間を
  どう走るか(経路・速度・障害物回避)はNav2の仕事。だから頂点に着けるかは
  Nav2次第で、Nav2が詰まればタスクも止まる。
- **直接割当 vs 入札**は、フリート運用の基本操作。「この1台にやらせたい」
  なら `-F -R`、「空いてる方に任せる」なら入札。次章からはこの入札の中身を
  開けていく。

## 確認課題

1. `-R toio1` と `-R toio2` を交互に投げ、指名した方だけが動くことを確認する。
2. `-F` `-R` を**両方外して** `dispatch_go_to_place -p patrol_B` を投げ、
   今度はどちらが動くか観察する。**なぜその1台が選ばれたのか**は次章の
   「入札」で説明できるようになる ── 今は「指名しないと勝手に選ばれる」
   ことだけ押さえる。
3. `navigate_to_pose/_action/status` を `/toio1` と `/toio2` の両方でechoし、
   直接指名したときに**指名した側にだけ**ゴールが立つことを見る。

「1台・1回」が追えたら、次は「巡回」でnavグラフそのものを理解する。
