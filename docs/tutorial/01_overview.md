## Open-RMF とは

**Open-RMF**(Robotics Middleware Framework)は、**複数台・複数メーカーの移動
ロボットと施設設備(ドア・エレベータ・搬送機)を、同じ空間で協調させる**ための
オープンソース基盤。ROS 2 の上で動く。

一言でいうと **「フリート(ロボットの群れ)の交通整理とタスク配分をする管制塔」**。
個々のロボットの走り方(自己位置推定・経路追従)は各社の実装(このチュートリアル
では Nav2)に任せ、RMF はその上で

- **どのロボットにどの仕事をさせるか**(タスク割当 → [章5](05_bidding.md) 入札)
- **同じ通路を使う複数台をどうさばくか**(交通調停 → [章6](06_traffic.md))
- **いつ充電に帰すか**(バッテリ管理 → [章7](07_battery_charge.md))

といった**フリート全体の意思決定**を担当する。

### なぜ必要か

倉庫や病院では、**別々のメーカーのロボットが同じ廊下を共有**することがある。
各社バラバラに動くと衝突や渋滞が起きる。RMF は**メーカー非依存の共通の交通・
タスク基盤**を提供し、各ロボットは「フリートアダプタ」という薄い通訳を書くだけで
この基盤に参加できる。

### toio はどう位置づくか

toio は手のひらサイズの1台数千円のキューブ型ロボット。これを**2台の小さな
フリート**に見立て、RMF のフリート処理(入札・交通調停・充電)を**卓上で・
シミュレーションから実機まで**学べるようにしたのがこのチュートリアル。倉庫の
数十m級ロボットと**同じRMFの仕組み**が、数cmのマットの上で動く。

## RMF固有の用語(先に押さえる)

以降の章で頻出する用語。今すべて理解する必要はなく、出てきたら戻る索引として使う。

| 用語 | 意味 | 主に扱う章 |
|---|---|---|
| **フリート(fleet)** | 同種ロボットの群れ。本パッケージのフリート名は `toio`(`toio1` / `toio2`) | [章2](02_architecture.md) |
| **フリートアダプタ(fleet adapter)** | RMFと個々のロボットの**通訳**。抽象タスクを各ロボットの走行指令へ翻訳し、位置・バッテリを報告 | [章2](02_architecture.md) |
| **EasyFullControl** | フリートアダプタを書くためのRMFのAPI。toioは走行をNav2に委譲する実装 | [章2](02_architecture.md) |
| **RMFコア(RMF core)** | 機種に依存しない中枢。ディスパッチャ・交通スケジュール・建物図サーバ等 | [章2](02_architecture.md) |
| **ディスパッチャ(dispatcher)** | 投入されたタスクをフリートに配り、入札結果で割当を決める | [章5](05_bidding.md) |
| **タスク(task)** | ロボットにやらせる仕事の単位。patrol / delivery / ChargeBattery など。**フェーズ(移動・荷役・充電)の列**でできている | [章3](03_go_to_place.md)〜 |
| **入札(bidding)** | 誰にタスクをやらせるかを決めるオークション。**BidNotice**(依頼)→ **BidResponse**(見積)→ 落札(award) | [章5](05_bidding.md) |
| **交通スケジュール(traffic schedule)** | 各ロボットの走行経路を**時空間で予約**し、かち合いを調整する大域の仕組み(`rmf_traffic_schedule`) | [章6](06_traffic.md) |
| **交渉(negotiation)** | 予約がかち合ったときに経路を譲り合う調停 | [章6](06_traffic.md) |
| **参加者(participant)** | 交通スケジュール上の1エージェント(≒1ロボット)。RViz可視化のマーカー名にも出る | [章10](10_visualization.md) |
| **navグラフ(nav graph)** | ロボットが走れる**頂点**(waypoint)と**レーン**(lane)の地図。自由空間ではなくこの上を動く | [章4](04_patrol.md) |
| **waypoint(頂点)** | navグラフの停留点。タスクで指定する `patrol_A` などがこれ | [章4](04_patrol.md) |
| **lane(レーン)** | 頂点間の通行可能な辺。双方向/一方通行がある | [章4](04_patrol.md) / [章6](06_traffic.md) |
| **建物図(building map)** | フロア図・navグラフ・設備をまとめたRMFの地図(`building_map_server` が配る) | [章2](02_architecture.md) |
| **ワークセル(workcell)** | 荷役を担う設備。払い出し機 **dispenser** と受け入れ機 **ingestor** | [章8](08_delivery.md) |
| **フリートアクション(perform_action)** | 標準タスクにない独自動作。toioではLED・効果音の演出 | [章9](09_fleet_action.md) |
| **finishing_request** | タスク完了後の片付けポリシー(toioは `charge`=チャージャーへ帰す) | [章4](04_patrol.md) / [章7](07_battery_charge.md) |
| **ChargeBattery** | 残量が閾値を下回る見込みのときRMFが**自動で計画**する充電タスク | [章7](07_battery_charge.md) |
| **Dock** | チャージャー到着の最終区間で使う精密停止(実機のキューブ内蔵走行)。A4のみ | [章11](11_real_robot.md) |
| **door / lift supervisor** | ドア・エレベータの調停役。toioの遊び場には不要なので本パッケージでは省略 | ── |

## 全体像(次章への橋渡し)

RMFの環境は**役割の違う3層**でできている ── 上が「何をするか(RMFコア)」、
真ん中が「このロボットで実現する(フリートアダプタ)」、下が「どう走るか
(Nav2 + Gazebo/実機)」。この三層を実際のノード一覧で確かめるのが次章。

**この章の用語がRMFコアとフリートアダプタの境界に集中している**のは偶然ではない ── 入札・
交通調停・充電という**フリート処理の核心がそこにある**からで、それをこの
チュートリアルで登っていく。

## 確認課題

1. 「フリート」「フリートアダプタ」「RMFコア」を、自分の言葉で1文ずつ説明できるか。
2. RMFが担当すること(タスク割当・交通調停・充電)と、Nav2が担当すること
   (自己位置推定・経路追従)の**境界**を言えるか。詳しくは次章で確かめる。
